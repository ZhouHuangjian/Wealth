# 财务管理系统：账单导入、证据关联与对账设计

状态：开发前设计稿。与 [领域模型](domain-model.md) 配套；本文没有宣称任何账单格式已经适配或通过真实数据验证。

范围与 [产品需求](product-requirements.md) 一致：用户已确认多个独立个人或家庭及彼此隔离；同用户可加入多个空间和 Owner/Editor/Viewer 角色是设计默认值。同家庭空间内账户共享，需要隐藏的私人账户放在私人空间。

## 1. 首批来源与兼容性状态

| 首批目标 | 希望取得的数据 | 当前状态 | 不可提前假定 |
|---|---|---|---|
| 广发期货 | 完整结算单、资金明细、成交与持仓、机构权益 | 待真实样本、格式与字段定义验证 | 盈亏字段口径、合约乘数、权益公式、导出编码 |
| 银河期货 | 完整结算单、资金明细、成交与持仓、机构权益 | 待真实样本、格式与字段定义验证 | 与广发期货相似的列名一定同义 |
| 喵喵记账 | 账户、分类、日常收支、转账、期初余额等导出 | 待真实样本、产品版本与字段语义验证 | 导出一定包含原始支付交易号、转账配对或投资细节 |
| 广发基金 | 产品及份额类别、交易申请、确认、份额、现金分红、净值、到账 | 待真实样本及具体产品验证 | 扣款日就是确认日、申请金额就是成交金额 |
| 易方达基金 | 同上，包含需要验证的 QDII 生命周期 | 待真实样本及具体产品验证 | T+2 可以统一写成两个工作日，或规则可套用其他基金 |

支付宝、微信、银行账单是用户原始需求中的补充来源；设计保留这些适配能力，但它们不替代本次确认的五个首批目标。港美股券商尚未确定，具体适配器待明确。

首批目标可以是 CSV、Excel、PDF 或其他实际导出格式；在拿到样本前不指定它一定支持哪种文件。加密压缩包/文件的解密流程单独处理，不将文件密码长期保存为账户密码。

## 2. 导入分层与提交原则

```text
原始文件 / 原始数据
  → 文件检测与格式版本识别
  → 规范化来源记录（保留原文及定位）
  → 同源重复检查 / 跨来源证据关联 / 账户与产品映射
  → 候选经济事项、快照、价格或对账证据
  → 用户预览与确认
  → 原子提交正式事件、分录、持仓及证据关系
  → 与机构余额 / 持仓 / 权益对账
```

解析成功只意味着文件能被读取，不意味着已经入账、已去重或已对账。预览前后的余额影响必须明确显示；未确认批次不得改变正式资产或收益。

来源记录可以扮演不同角色：新的真实事件、已有事件的补充证据、机构快照、行情/净值、期初事实，或仅为无法入账的参考记录。系统不能把结算单每一行都当作现金流水。

## 3. 规范化字段

### 3.1 所有来源记录的共同字段

| 字段 | 要求及用途 |
|---|---|
| tenant_id、record_id | 必填；租户隔离和系统内部唯一身份 |
| source_institution、source_product、source_account_ref | 来源机构、来源产品/渠道、原账户引用；缺失时待用户映射，不能由名称猜测 |
| artifact_id、raw_locator | 对应文件及页/工作表/行/原始记录定位 |
| artifact_sha256、adapter_id、adapter_version、format_version | 原始文件内容身份和可复现的解析版本 |
| record_kind | transaction / position / balance / equity_snapshot / price / order_status / reference 等 |
| native_record_id、native_parent_id、native_order_id | 来源稳定身份，分别用于记录、退款/原单关系、业务订单关联，可空 |
| original_text、original_fields | 保留原始单元格/文本或安全存储引用；规范化结果不覆盖原文 |
| source_status、normalized_status | 来源原始状态及系统映射状态；未知状态不默认成功 |
| warnings、errors、field_provenance | 问题清单与字段来自原文、用户映射还是规则推导的标记 |

### 3.2 交易和现金流字段

| 字段 | 要求及用途 |
|---|---|
| event_type、direction | 消费、退款、内部转账、买卖、申赎、分红、利息、费用、结算等；未知时为待分类 |
| amount、currency | 十进制字符串及币种；先保留来源金额和方向，再映射经济含义 |
| gross_amount、net_amount、fee_amount、tax_amount | 可空、分别保存；明确各数值是否含费以及币种，不能同时作为独立支出重复入账 |
| occurred_at、posted_at、trade_date、settlement_date | 各时间语义独立，原文只有日期时保存 date_precision；时区缺失则标记 |
| counterparty、merchant、description、category、tags | 来源值与系统映射值分开保存；名称不作为可靠唯一身份 |
| payment_channel、funding_account_hint、receiving_account_hint | 支付渠道和实际出/入资金账户；微信不必然意味着微信余额账户减少 |
| transfer_group_id、refund_of_native_id | 有原始关联时优先使用；缺失不自动伪造 |

### 3.3 投资、结算和估值字段

| 字段 | 要求及用途 |
|---|---|
| instrument_source_code、market、share_class、instrument_id | 原始产品身份及映射；基金名称相似时必须确认代码和份额类别 |
| quantity、price、price_currency、contract_multiplier | 原始数量/价格/乘数独立；不能假设期权一律某个乘数 |
| side、position_effect、lot_reference | 买卖方向、开平/持仓变动语义、批次引用，只有证据支持才填 |
| application_at、debit_at、nav_date、confirmed_at、units_available_at、cash_settled_at | 基金申请、扣款、净值归属、确认、份额可用、到账各自独立 |
| balance_as_of、statement_period、equity、available_cash、margin、frozen_amount | 机构时点和期间数据及原始字段定义；是否构成权益必须经验证 |
| realized_pnl、unrealized_pnl、settlement_pnl、pnl_basis | 不混淆不同盈亏；未知口径保留原值并标记不可汇总 |
| price_as_of、published_at、valuation_kind | 区分正式净值、盘中估值、成交价、手工估价等 |
| fx_base、fx_quote、fx_rate、fx_as_of、fx_source | 真实兑换和报表估值汇率分开，明确方向 |
| evidence_coverage | 该记录覆盖账户、子范围、日期、币种和数据类型，用于阻止重复汇总 |

不是每类记录都必须具有全部字段，但每类适配器必须声明最少必填字段。所有非空金额、数量、价格和汇率必须通过精确十进制校验；缺失字段不能填成 0。

## 4. 适配器接口约定（描述，不是应用代码）

每个适配器应公开以下能力：

1. **detect：**输入文件类型、有限安全样本及用户选择的来源，返回候选来源、格式版本、可信度和识别理由。格式冲突时要求用户选择，不仅靠文件名。
2. **validate_structure：**检查表头、编码、页结构、期间、账户标识、币种与关键列；返回阻断问题及可修复问题。新增未知关键列或状态进入人工审查，不能静默丢弃。
3. **parse：**输出规范 SourceRecord、原始定位、解析诊断和文件摘要。不得直接写正式账本。
4. **identify：**提供来源记录身份规则、身份可靠等级及稳定字段。明确来源 ID 是全局、账户内、业务订单内还是每日范围内唯一。
5. **map_semantics：**将已验证的来源类型/状态映射为候选事件、快照或证据角色，列出依据和未知项。不能替代用户确认账户归属。
6. **validate_totals：**在文件提供控制合计时核对记录数、收入/支出、资金变化、持仓或权益；说明使用的公式和格式版本。
7. **capabilities：**声明支持的 record_kind、格式版本、市场、币种、账户类型、退款关联、原生身份字段和已知缺口。

适配器输出需要确定性：相同文件、适配器版本和映射配置产生相同规范结果。重处理时创建新解析版本，与原结果比较，不覆盖原证据或已提交事件。

映射规则分为全局格式规则和租户自定义规则。某家庭把某商户映射为“工作报销”，不能影响其他家庭。分类规则可以自动建议，资金账户、产品身份、跨币种以及差异处理应有更严格的确认门槛。

## 5. 幂等：批次、记录和提交三个层次

### 5.1 文件与批次

- 原始文件身份：`tenant_id + SHA256(原始文件字节)`。同租户同文件可以复用已有文件对象，跨租户不返回哈希命中信息。
- 解析身份：`artifact_id + adapter_id + adapter_version + format_version + mapping_revision`。映射变更形成新预览修订，不代表新的经济事项。
- 用户入账请求使用随机 `Idempotency-Key`，与技术契约统一为 `(tenant_id, actor_id, command_scope, key)` 唯一，并保存规范请求摘要。同键同请求重试返回原结果；同键不同请求返回 409。日志 request_id 只用于排错，不代替幂等键。HTTP 幂等与来源事实永久去重独立。
- 同内容重新导出可能导致文件字节变化，所以文件哈希只能处理完全相同文件，不能替代逐条去重。

### 5.2 同源记录身份

有可靠原生记录号时：记录键由 tenant_id、source_namespace、来源账户、原生记录号、记录类型组成，并加入该来源声明需要的日期/子行号。订单号如果覆盖申请、确认、费用和退款多行，不能单独作为唯一记录键。

没有可靠 ID 时：用经格式验证的稳定字段生成候选指纹，包括来源账户、原始发生日期及精度、币种、方向、金额、来源类型、描述/对手和可用参考号。**候选指纹不是自动删除依据。** 同一天同金额同商户确实可以消费两次，应保留重复候选供确认。

页/行号用于原始定位，不作为重叠期间导出的稳定身份。相同原生身份但内容变化时，标为来源修订或状态更新，保留新旧记录并要求确认，不静默用新文件覆盖旧账。

### 5.3 经济事项和正式提交

正式事件使用独立 event_id 与阶段身份，属于一个 Operation 生命周期。扣款、确认、退款是不同阶段，分别保留不可变事件；同阶段多来源只补证据，不创建第二次现金影响。`(tenant_id, operation_id, stage_instance_id)` 标识唯一阶段，允许多次部分成交拥有不同阶段身份；更正通过冲正／替代链保证一个有效版本。EventEvidence 约束同一记录与阶段不重复关联；汇总证据可以支持多个明确不重叠的阶段，不是把来源行号全局限制为只能引用一次。

入账幂等需要同时检查：预览版本仍有效、待提交的来源事实／阶段尚未产生重复经济影响、主事件版本未变化、CoveragePolicy 未冲突、用户仍有权限。已存在来源记录允许复用，证据关联按记录与阶段去重。检查和提交在同一事务中完成；另一编辑者先提交时应返回冲突并刷新预览。

## 6. 同源重复与跨来源关联

| 情况 | 处理方式 |
|---|---|
| 完全相同文件再次上传 | 展示已处理批次与结果，可查看或用新解析器重处理，不自动再入账 |
| 同一机构重叠日期账单出现同一稳定记录号 | 标为同源重复，引用已存在来源记录；没有变化则不新建事件 |
| 同来源、同原生身份但成功/退款/撤销状态变更 | 标为修订/状态变化，依实际事实增加或更正事件，不作为普通重复删除 |
| 银行和微信都记录同一消费 | 关联到同一经济事项，保留两个来源证据 |
| 喵喵记账已记录某基金扣款，基金确认单随后到达 | 先关联同一申购生命周期；补充份额和成本，不再次扣减现金 |
| 两笔相同金额且时间接近、无可靠关联号 | 仅推荐关联，由用户确认；不自动合并 |
| 汇总结算单和逐笔成交明细同时存在 | 按覆盖范围及数据角色处理，不能把汇总行再当新交易 |

跨来源匹配的证据强度依次考虑：可验证的业务/支付关联号、出入账户身份、币种与净额/费用解释、时间区间、商户或产品身份、摘要。规则输出匹配理由及冲突，而不仅给出难以解释的置信分。

时间窗口按来源和事件类型配置；跨时区、工作日延迟、基金确认和跨币种转账不能套用统一“前后一天”。金额不同只有在费用、汇率或拆分有依据时才可关联。

## 7. 关键数值案例

### 7.1 银行卡通过微信消费：三条来源，一次消费

银行流水显示 -100 CNY；微信记录某商户支付 100 CNY、付款方式为该银行卡；喵喵记账中也有餐饮支出 100 CNY。

确认三条来源对应同一交易后，只形成一次借记餐饮费用 100、贷记银行卡 100。微信是支付渠道，不减少微信余额。三条证据均可追溯。

如果微信只给出“银行卡”且无法识别实际卡，或喵喵记录时间/金额不一致，则进入待确认；不能仅凭同日同金额自动合并。

### 7.2 部分退款

上述 100 CNY 消费后来退款 30 CNY，微信退款记录和银行入账 +30 CNY 关联为同一退款事件，并指向原消费。结果为现金净减少 70、净消费 70；不是新增收入 30。

退款金额不得因双来源变成 60。累计已确认退款超过原消费金额时应提示检查，可能存在多单合并、汇率/费用差异或错误关联，不可直接吞掉差额。按退款实际生效日期入账，历史报表是否重算另由报告政策决定。

### 7.3 内部转账与手续费

从银行卡 A 转出 10,000 CNY，银行卡 B 收到 9,998 CNY，并有 2 CNY 手续费证据：借记 B 9,998、借记转账费用 2、贷记 A 10,000。收支报表只把费用 2 列入支出，转账本金不计收入/支出。

如果只有 A 的 -10,000 或 B 的 +9,998，则可显示已知一侧及待匹配清算项；不要猜测另一侧或手续费。资金确实暂未到账时，使用经过确认的在途账户。后续到账清除在途，不能再增加一次净资产。

### 7.4 基金扣款与延迟确认

喵喵记账或银行显示扣款 1,000 CNY，基金申请记录金额同为 1,000；此时可以确认现金流与申购在途，但尚不能推断份额。

后续正式确认记录给出 995 份、每份成本 1 CNY、费用 5 CNY，则在本例明确采用的费用单列政策下，将 1,000 在途转为 995 投资成本与 5 费用，增加 995 份持仓。按首版默认管理口径并入该账户产品的移动加权平均成本池，同时保留本次真实批次与机构报告成本；不能把管理成本称为税务成本。三类来源关联同一个订单生命周期，不再次扣款。

扣款与确认各是一笔不可变阶段事件：确认只消除在途并建立持仓，不能更新旧扣款分录或重新提交整笔扣款。部分确认使用独立阶段身份，累计确认／退款金额与原扣款及明确费用核对。

该例不代表任何实际基金费率。若真实确认数据的净值、金额与份额存在舍入关系，必须使用该产品经验证的精度规则。QDII 的 T+2 只保留为待验证规则，不用于生成虚构确认日期。

### 7.5 期货结算与明细

机构期初权益 100,000 CNY、期间入金 10,000、出金 0、期末权益 112,000。在两个快照范围与口径一致、且无其他外部资产变动时，可计算“扣除净入金的权益变化”为 2,000，但在费用、结算和其他调整分项未核实前，不把它直接命名为“已实现交易收益”。

若结算单还列有 2,000 的结算收益或某项持仓盈亏，必须核实其是否已包含在期末权益中；不能将其再加成 114,000。逐笔成交记录在快照模式中可用于解释和对账，不重复贡献权益。

新银行出入金早于新权益快照到达时，按[快照资金滚动规则](domain-model.md#63-快照之后的已知出入金)处理在途、已证实到账调整与新快照吸收。解析器输出各出入金的期间及覆盖信息，不能将到账顺序当成经济发生顺序；无法确定覆盖就显示缺口。

### 7.6 实际还款的拆分晚到

已证实银行扣款 4,000、但本金／利息尚缺时，可以先形成银行减少与还款待分配清算。预览必须说明现金已确定、负债及费用尚未确定，净资产不能标为完整。后续贷款单确认本金 2,500、利息 1,500，只追加清算拆分，不再扣银行；对应同一还款期次的来源重复则只补证据。

## 8. 预览、确认与批次状态

批次状态建议：uploaded → parsing → needs_mapping / needs_review → ready_to_commit → committed；另有 parse_failed、cancelled、reversed。对账状态单独保存，不把 committed 自动等同于 reconciled。

预览至少展示：

- 识别来源、格式版本、账单期间、账户、币种、记录数和控制合计。
- 新增事件、补充证据、同源重复、修订、快照、待匹配、错误各自数量。
- 逐项关联理由、原始定位、目标账户/产品/分类及操作后的现金/持仓影响。
- 批次入账前后各账户原币余额变化，以及对净资产的预计影响。
- 不能确认的字段、预估日期、缺失汇率、精度问题、覆盖冲突与对账差异。

阻断条件包括：租户或权限不符、金额无法解析、币种未知、必要账户/产品未映射、无法解释的分录不平衡、稳定记录 ID 冲突、覆盖范围冲突、关键总数/合计不符、格式关键语义未知。普通分类缺失可以由用户选择“待分类”后入账，但不能绕过资金方向等核算缺失。

默认按批次原子提交。确需部分导入时，先显式拆成独立子批次，保留未处理记录和原文件合计差异说明；不能只导入“看起来没问题的行”却宣称整个文件完成。

预览确认后，如果映射、数据、权限或已有事件发生改变，原确认失效并要求刷新。UI 需要区分“确认导入这些新事件”和“只关联为已有事件的证据”。

## 9. 撤销、冲正与审计

- 尚未提交的批次可以取消；不影响正式账本。
- 已提交批次通过冲正处理，不能直接删除分录或修改原始文件。冲正保留原事件、对应反向影响、操作者、理由与生效日期。
- 账本按原分录、反向分录和替代分录的净额计算；不能先排除原分录再扣一次反向分录。业务上展示当前有效版本，不等于删去原分录的历史影响。例如期初 100、误记支出 80、更正为 60，冲正与替代后余额应为 40、净支出 60。
- 一批文件如果只新增证据关联，撤销只撤回该批的关联，不撤销由其他来源已确立的经济事项。
- 如果后续卖出已依赖本批买入持仓、退款依赖本批消费、或对账依赖本批期初余额，撤销前列出依赖并阻断不一致的孤立冲正；必要时建立包含相关更正的修订方案。
- 撤销后重新导入，应识别历史来源记录和冲正链，建立明确的替代事件，不因“已存在”而丢掉有效更正，也不重新激活旧事件。
- 数据保留删除与财务冲正是不同操作。owner 删除敏感文件不自动删除其已经形成的财务事实；可保留哈希、脱敏定位和删除审计，具体保留政策待确认。

## 10. 对账状态与核对维度

### 10.1 状态

| 状态 | 含义 |
|---|---|
| not_started | 尚未选择机构对照证据或截止时点 |
| insufficient_evidence | 只有单侧数据、缺失期初/期间流水/持仓或机构定义 |
| in_progress | 正在核对，存在待匹配、在途或差异 |
| matched | 同一范围、时点、币种和口径下，必要项目均按既定容差匹配 |
| exception_accepted | owner/editor 已记录并接受明确差异；必须显示“有差异”，不能标为 matched |
| stale | 新导入、事件更正或来源修订使原对账结论需要复查 |

对账结论绑定具体数据版本、来源、范围和截止时点；新事件进入已核对期间时使相关状态变为 stale。

### 10.2 核对维度

1. **文件完整性：**文件期间、页数/行数、账户、导出合计以及解析失败数量。
2. **现金：**在机构字段定义允许时核对期初 + 流入 − 流出与期末；按币种分别比较，不以汇率折算后的相近金额掩盖原币差异。
3. **持仓：**按账户、产品代码/份额类别、方向等身份核对数量；未确认申请不能冒充有效份额。
4. **成本和收益：**本系统默认管理成本为移动加权平均，保留真实批次及机构报告口径；费用单列/成本化政策必须显式且不可双扣。只有双方成本/费用政策与期间口径一致才直接比较；“机构成本”与“本系统成本”可并列，差异不能自动调平。首版收益率验收为 XIRR 类口径及收益分项，不增加 TWR 实现要求。
5. **权益与保证金：**按已验证的机构字段关系核对，保存公式版本；名义金额与保证金不额外计入净资产。
6. **在途与跨期：**区分真实延迟和漏单，保存预计/实际到账事实及原因；T+2 不作为自动关闭差异的依据。
7. **汇率与估值：**核对价格时点、正式/估算状态、汇率方向与来源；现金账平衡不等于投资市值已一致。

容差按币种、金额/数量类型及机构精度配置，默认以来源精度做精确核对。超出容差的差异保留为待处理；“差一分钱”也要知道是舍入、手续费还是缺失证据。

## 11. 原始敏感文件的存储与访问

- 原始账单使用与网页公开资源分离的私有存储，传输加密、静态加密；对象存储键使用不可猜的内部 ID，不包含姓名、证件号或完整账号。
- 原始文件下载和完整账目/配置导出默认仅 Owner 可执行。Editor 可以在导入与核对页面查看必要原始行和定位，不能下载整份原件；Viewer 只读页面，不具有原始证据读取或导出权限。局部错误结果导出也需要明确的操作权限，不能成为绕过整份原件限制的通道。
- 每次上传、解析、预览、下载、导出和后台读取都校验租户与权限。禁止只知道文件 URL 即能读取；下载使用短期授权或服务端受控传输，并考虑成员撤销后链接失效。
- 默认不把原始文件、姓名、账号、证件号、交易摘要或单据正文写进应用日志、异常监控或开发演示数据。日志保留内部 ID、错误类别和脱敏定位。
- 开发验证使用用户授权的脱敏样本；脱敏时保留币种、精度、字段结构、关联号一致性与控制合计关系。真实文件不提交到代码仓库。
- 不默认上传账单到外部 AI 服务。以后如需 OCR/模型解析，必须明确处理方、发送范围和保留政策，并保留可审查的解析结果。
- 文件保留时长、导出/删除能力、备份加密与恢复权限由产品决定；到期删除应覆盖缓存和临时解析文件，备份采用明确的过期策略。
- 哈希仅用于内容身份，不是匿名化；不能向其他租户泄露某文件已存在。全局去重若会暴露存在性，首版不采用。

## 12. 格式版本与验证标准

每个首批来源至少取得：普通记录、退款/撤销、转账或入出金、费用、空记录/异常记录、跨月期间、重叠导出、同金额不同交易，以及该来源适用的持仓/结算/确认样本。无需强求所有来源都有所有类型，但缺失类型要显式列入能力边界。

期货建议样本覆盖连续结算日和入出金；基金建议覆盖申请至确认/到账的完整链条，至少包含一次跨期和适用的 QDII 案例；喵喵记账样本应包含账户间转账、退款以及已手工记录投资扣款的情形。

格式注册表记录来源、产品版本、格式标识、表头/特征、首次验证日期、样本覆盖、已知限制与适配器版本。未知格式不沿用旧解析器强行入账，而是识别为待适配。

正式声称“兼容”前，需要以下可复现验证：

- 所有金额/数量原文能无损解析，文件控制合计通过。
- 同文件、重叠导出、重试和并发提交不重复产生正式事件。
- 同日同额不同交易不被误删；同交易跨来源不重复入账。
- 银行卡微信消费、部分退款、内部转账、申购在途和确认均能说明余额影响。
- 不同租户不能读取、匹配、下载或引用彼此记录；后台任务及导出同样隔离。
- 权益快照与明细同时导入不会重复增加资产。
- 修改/撤销后，相关持仓依赖和对账状态正确变化。
- 缺失字段、未知状态、格式更新、汇率缺失及来源修订都会产生明确可处理状态。

## 13. 待验证风险与当前结论

当前最大的阻碍是缺少实际账单样本和字段定义，因此现在可以完成结构、接口和验收设计，但不能承诺五个来源已经兼容，也不能承诺期货逐笔复算与机构结果一致。

需要首先补齐：五个来源各自真实且脱敏的导出样本；同一笔基金交易的申请、扣款、确认和到账证据；广发与银河期货的连续结算单；喵喵记账记录与机构记录的重叠案例；具体港美券商以及具体基金代码/份额类别。
