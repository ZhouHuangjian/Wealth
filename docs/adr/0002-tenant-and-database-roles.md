# ADR 0002：多空间隔离与数据库角色

- 日期：2026-09-25
- 状态：实施约束，验证结果见开发状态

## 决议

空间是财务数据隔离边界；同一用户可以加入多个空间，每个请求在指定空间重新验证成员资格和角色。Viewer 不能写入，原文件与完整导出默认仅 Owner 可获取。后台任务执行、结果生成和文件下载都重新授权，不把创建任务时的权限视为永久授权。

应用的空间过滤、跨空间关联检查与 PostgreSQL RLS 同时存在。数据库运行角色 `wealth_app` 不是表所有者，没有超级用户、建库、建角色、复制及 `BYPASSRLS` 权限；迁移角色 `wealth_owner` 拥有模式与表，用于受控迁移。必要私有表启用并强制 RLS，未建立有效上下文默认拒绝。后台批处理需逐空间建立上下文，事务结束后不应留下连接状态。

`compose.yaml` 的 web、worker、beat 仅获得 runtime URL。只有临时 `migrate` 服务获得 owner URL；PostgreSQL 初始化账号不进入应用容器。迁移与恢复工具具有运维权限，不是提供给普通成员的公开接口。

SQL 初始化脚本将表与序列的默认权限授予 runtime，但不授予 `TRUNCATE`、建表或改变 RLS 的权限。新私有表是否真的启用 RLS、关联约束是否包含空间，以及无上下文的请求是否失败，仍须由测试验证；角色命名本身不是安全证明。

## 操作后果

- `.env` 改密码不会修改已经初始化的数据库角色密码，须在维护窗口显式轮换。
- 测试环境临时授予 owner 建库权限，只用于隔离测试库，不应用于生产配置。
- 备份由数据库运维账号读取全库；备份及解密密钥的访问权限等同全空间运维权限。
- 跨空间文件、搜索、导出、缓存、异步任务和外键均纳入验收，不能只验证列表接口。

数据库所有者和特权角色有 RLS 例外，因此测试必须实际使用 runtime 角色。[PostgreSQL RLS 官方说明](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)
